# Chapter 6 — Kafka and Asynchronous Processing

## The vocabulary

- A **topic** is a named append-only stream of records. AetherFlow's dispatch
  topic is configured as `aetherflow.jobs` by default.
- A **partition** is an ordered log within a topic. Ordering is per partition,
  not global. The producer keys a record by job UUID, which keeps a job's
  records on the same partition under Kafka's normal partitioner.
- A **producer** serializes and sends dispatch records. The adapter awaits
  `send_and_wait`; default `acks="all"` asks the in-sync replica set to
  acknowledge, but local Compose has a single broker.
- A **consumer group** divides partitions among consumers in that group. A
  partition is assigned to at most one active group member at a time; adding
  workers beyond partition count does not add useful active partition
  parallelism.
- An **offset** is a record position. AetherFlow disables auto-commit and
  commits the received offset only after the worker's processing decision.

The envelope is versioned JSON (`aetherflow.job-dispatch.v1`) containing a job
ID, job version, enqueue timestamp, and schema version. The Kafka record is a
dispatch notification, not the complete job or its result.

## Delivery and ordering

If the process fails before committing the Kafka offset, Kafka can deliver the
record again. The worker's persisted state/version checks make many duplicate
or stale records durable no-ops; they do not make provider side effects
exactly once. A new retry is represented by a new job version and a new
outbox record with a due time. Kafka order alone does not enforce lifecycle
order across PostgreSQL commits, multiple dispatches, or retry timers.

Default producer idempotence reduces duplicate records generated by producer
retries within Kafka's supported producer session semantics. It cannot close
the separate database-finalization gap in the outbox, nor deduplicate a
provider request after a worker crash.

## Unavailable broker, backpressure, and diagnosis

When Kafka is unavailable, the API can still durably accept immediate work
while PostgreSQL is healthy: the outbox intent remains the publication
boundary. The publisher cannot complete delivery; it records retriable
failures where it can reach PostgreSQL, and the queue of unpublished intents
can grow. When Kafka is reachable again, the publisher can retry due rows.
Readiness checks PostgreSQL, not Kafka, so API readiness is not proof that
dispatch is flowing.

Backpressure currently comes from the bounded outbox publication batch,
publisher polling, Kafka partitions, worker process count, provider latency,
timeouts, and database pool. The worker loop processes records sequentially
per consumer instance; adding a consumer only helps up to available partitions
and safe DB/provider capacity. The repo does not claim a tuned throughput
limit.

For a backlog: compare unpublished outbox count/oldest age and dispatch
failures with Kafka connectivity and lag; check scheduler due count; then
inspect worker logs, active leases, attempts, provider failures, and database
availability. Metrics are process-local, so an external scraper must collect
each live process for operational use.

## Why Kafka, and what else could fit?

Kafka is useful when a durable replayable partitioned stream and consumer
groups justify an independently operated broker. The repo records Kafka
dispatch intent in ADR-0003/0005/0012 and deployment rationale in ADR-0017;
do not claim unrecorded alternatives were part of the original selection.

| Alternative | Benefits | Costs / when it may fit better |
|---|---|---|
| PostgreSQL polling queue | Fewer moving parts; transactional claim and job data in one system; reasonable for modest workloads. | DB polling and row contention can become coupled to application reads/writes; choose when broker scale/replay is not needed. |
| Redis-backed queue | Familiar fast enqueue and delayed jobs; useful if Redis queue semantics already fit operations. | Redis persistence/HA and job semantics must be configured; AetherFlow's Redis is only optional rate limiting. |
| RabbitMQ | Routing, acknowledgements, work-queue semantics; suitable for command/task delivery. | Different operational/throughput model; adds another broker boundary. |
| Managed cloud queue | Less broker operations for a single cloud deployment; dead-letter and visibility-timeout features may help. | Cloud coupling, quotas/cost, and less portable local parity. |
| Direct synchronous provider call | Simplest when tasks are short, low-volume, and retry semantics are unnecessary. | Couples caller availability/latency to provider and loses durable asynchronous lifecycle. |

**Interview answer:** Kafka is a documented dispatch design choice, not
proof that Kafka is universally superior. If measured traffic and replay needs
did not justify a separate broker, a PostgreSQL queue might be simpler; that
would be a legitimate architecture, not an inferior one by default.

# Chapter 7 — PostgreSQL and Data Consistency

## Actual persistent model

| Table | Purpose |
|---|---|
| `users`, `roles`, `user_roles` | Identity and current database-backed role membership. |
| `refresh_sessions`, `api_keys`, `audit_logs` | Rotating refresh-session family, hashed API credential material, and administrative/security audit records. |
| `jobs` | Owner, input/configuration, state/version, schedule, execution lease, retry policy and lifecycle timestamps. |
| `idempotency_records` | Principal/key uniqueness, request fingerprint and original job. |
| `job_events` | Append-style state and lifecycle audit history. |
| `job_attempts` | Numbered execution attempts, worker/provider/error/usage/trace metadata. |
| `job_results` | One normalized result row per job. |
| `outbox_dispatches` | Versioned dispatch intent, publication state, lease, attempts and retry timing. |

The SQLAlchemy models are the current object mapping; Alembic revisions are
the schema history. Migration `0001_identity_access` establishes identity,
sessions, keys and audit tables. Later revisions add jobs/retries,
`0006_durable_scheduling` adds `schedule_at` and due indexes, and
`0007_demo_role` adds demo-role support. The migration chain, not `create_all`,
is the reproducible schema contract.

Important constraints/indexes include unique user email, role name, refresh
token hash, API-key public ID, `(user_id, idempotency_key)`, per-job attempt
number, one result per job, and dispatch uniqueness by job/version. Indexes
support owner/state listing, active leases, due schedules, outbox eligibility,
session expiry, and lookup by public credential ID. See each migration for
the authoritative DDL.

## Transaction and concurrency boundaries

- Submission commits the job, idempotency record, event, and immediate outbox
  intent as one unit.
- Scheduler activation commits compare-and-set state/version change, event,
  and outbox intent as one unit.
- Execution failure plus `RETRY_SCHEDULED` and its next dispatch intent is
  committed atomically.
- Provider I/O occurs outside database transactions.
- Outbox Kafka I/O occurs outside the short claim/finalization transactions.
- Result, attempt completion, and final success transition are not one
  database transaction; lease recovery reconciles a durable result with
  `SUCCEEDED`, otherwise an expired execution becomes `FAILED`.

Optimistic version predicates and row locks protect lifecycle transitions.
Unique constraints close duplicate-record races. PostgreSQL `SKIP LOCKED` is
used for bounded claim work where supported; current SQLite unit tests do not
prove its production concurrency behavior.

The async SQLAlchemy engine uses a per-process pool (`pool_size` default 5,
`max_overflow` default 10, with configured timeout/recycle). A connection
budget is approximately the sum of API, publisher, scheduler, and worker
process pools across replicas, plus migrations/admin tasks. Scaling processes
without budgeting connections can exhaust PostgreSQL even when each pool looks
small.

## Evolution and larger-scale options

Additive migrations should precede code that needs new fields; remove/rename
only after old code is gone. Backfills need bounded batches and an explicit
rollback/recovery plan. Large tables may need retention/partitioning for
events, attempts, audit and outbox; hot job rows may need separate read models
or archival. Do not split data prematurely: PostgreSQL currently simplifies
the consistency boundary that motivates the outbox.

### Isolation questions

At read-committed isolation, two concurrent actors can both observe an
eligible state. Correctness therefore depends on row locks, unique
constraints, lease-owner predicates and compare-and-set version updates—not
the assumption that a read remains current. Test actual PostgreSQL lock races,
deadlocks and lease expiry before claiming concurrency guarantees.

# Chapter 8 — Worker Reliability, Leases and Retries

## Claim and execute

For an eligible dispatch, the worker reloads the job and compares message
version/state with persisted state. It records `RUNNING`, increments state
version, sets `execution_owner` and `execution_lease_until`, and records the
attempt before calling the executor. State transitions are guarded by both
expected state and version. Provider code receives an immutable
`ExecutionRequest`; it does not hold a database transaction open.

Leases bound how long a worker's claim is considered live. A lease is not a
remote cancellation primitive and does not fence a provider that ignores
cancellation. State/version checks fence stale durable writes after another
actor changes the row, but cannot reverse an external side effect already
performed.

## Retry policy as implemented

Current execution retries are limited to `RATE_LIMIT`, `TIMEOUT`, and
`TRANSIENT_PROVIDER`. Backoff is bounded and deterministic (capped
exponential-style timing); configured `jitter` is accepted but not applied.
The retry budget comes from the job request. When exhausted, the job becomes
`FAILED`; retryable attempts otherwise atomically record the attempt result,
transition to `RETRY_SCHEDULED`, and create the future outbox row.

`UNEXPECTED` is a known discrepancy: ADR-0015 describes unexpected internal
failures among retry candidates, but the current retryable-category set does
not include it. Explain current source behavior, not the older intention.
Do not silently call every exception retriable. The separate outbox publisher
also has its own bounded dispatch retry policy; it is not the execution retry
counter.

## Crash and recovery cases

| Failure window | Durable evidence | Current recovery / residual risk |
|---|---|---|
| Before execution claim commit | Job not durably `RUNNING`; Kafka offset not committed on unhandled processing failure. | Record can be redelivered; claim is attempted again. |
| After claim, before provider call | `RUNNING`, attempt and lease exist. | Stale lease scan resolves to `FAILED` if no result; work is not resumed. |
| Provider performed work, worker died before result commit | Lease/attempt exist; external service may have acted. | Recovery cannot know provider effect; retry/re-delivery can repeat the external request. |
| Result committed, final transition missing | Durable unique result plus nonterminal job may remain. | Expired-lease recovery chooses `SUCCEEDED` when result exists. |
| Failure finalized with retry intent | `RETRY_SCHEDULED` and future outbox row commit together. | Publisher sends when eligible; duplicate dispatch is state/version checked. |
| Cancellation races an in-flight provider call | `CANCEL_REQUESTED` may coexist while call runs. | Completion may still end `SUCCEEDED` or `FAILED`; cancellation cannot promise remote abort. |

The precise stale recovery result is intentionally explicit: expired work is
not re-executed automatically; an existing result reconciles to success,
absence of a result resolves to failure. This preserves a durable terminal
state while honestly accepting possible lost/duplicated provider work.

## Graceful shutdown and stuck-job diagnosis

The worker is a long-running async process and Kafka auto-commit is disabled.
Do not claim that shutdown safely cancels every provider request: the provider
may already be executing remotely. A production shutdown protocol should stop
fetching new messages, bound the drain period, leave unfinished offsets
uncommitted, and let lease recovery reconcile the claim.

For a job stuck in `QUEUED`, inspect the matching outbox row, publish state,
Kafka connectivity/consumer lag, then worker availability. For `RUNNING`,
inspect owner/lease expiry, attempt start/completion, timeout, result
presence, and worker logs. For repeated `RETRY_SCHEDULED`, inspect failure
kind, attempt count, `retry_at`, provider health and rate limits. Correlate by
job ID, request ID and trace ID; redact prompt/credential material.

# Chapter 9 — Scheduling

## Stored schedule and due activation

A one-shot schedule is `jobs.schedule_at`, a timezone-aware timestamp
normalized to UTC. A future submission remains `ACCEPTED` and has no
dispatch intent. A past or immediate submission follows ordinary dispatch.
Migration `0006_durable_scheduling` adds a direct schedule index and a
composite due index `(state, schedule_at, created_at)`.

The scheduler polls due `ACCEPTED` records in a bounded batch. It uses
PostgreSQL row claiming/locking and a state/version compare-and-set to change
the job to `QUEUED`, write a lifecycle event, and create an outbox dispatch
in one transaction. It then yields transport publication to the outbox
publisher. A concurrent scheduler should skip locked work or fail its
compare-and-set rather than activating the same current version twice; the
database uniqueness and state/version conditions are the safety boundary.
Multi-process PostgreSQL behavior remains unverified by SQLite tests.

The scheduler uses UTC instants rather than local wall-clock interpretation.
This avoids ambiguous local times at DST boundaries; API validation rejects
naive timestamps. Clock skew still matters for due cutoffs and leases.
Production replicas should use synchronized clocks and monitor schedule
lateness. Poll interval and batch size trade dispatch latency against database
poll load.

## Cancellation and restart

In the current working tree, cancelling a scheduled job while it remains
`ACCEPTED` changes it directly to `CANCELLED`; it never enters the scheduler
due query. If activation wins the race and state becomes `QUEUED`, cancellation
uses the ordinary cancellation path. A stale already-published dispatch is
checked against current state and becomes a no-op.

Schedules survive scheduler restart because they live in PostgreSQL. The
restart process resumes polling due rows; no in-memory timer is required.
Current tests cover UTC normalization, due activation, duplicate polling,
cancellation, and idempotency conflicts, but process restart and real
PostgreSQL races are not established.

Only one-shot timestamps are implemented. Cron/recurrence would need a
schedule definition separate from each execution, timezone rules, missed-run
policy, per-occurrence idempotency, and bounded catch-up semantics. A managed
workflow scheduler or database-backed poller may be preferable depending on
complexity; a separate scheduler service is justified only if load or
operational isolation requires it.

# Chapter 10 — AI Provider Integration

## Boundary and data contract

`JobExecutor` in `jobs/execution.py` accepts an immutable execution request
and returns an `ExecutionOutcome` or raises normalized `ExecutionFailure`.
The resolver in `jobs/providers.py` selects the configured adapter. The
deterministic mock is the default and makes local tests/demos independent of
network access and API secrets. The OpenAI-compatible adapter uses HTTPX and
normalizes HTTP/provider failures and timeouts.

The accepted job input/configuration is Pydantic-validated at the API
boundary. The provider outcome is normalized as a dictionary plus optional
usage, `schema_version`, provider and finish reason. That is not a
job-type-specific typed output schema or proof that every arbitrary output
conforms to a customer JSON Schema. Do not describe it as stronger validation
than it is. Input configuration that looks like credentials is rejected;
credentials belong in runtime environment/settings, not a job payload.

There is no configured automatic multi-provider fallback in current source.
The worker retries selected normalized transient classes, but a different
provider is not silently selected as a fallback. An external provider brings
latency, availability, cost, quota, data-residency and output-drift risks.
Never include API keys in logs, job config, screenshots, or interview demos.

## Choosing the boundary

Provider-specific SDK calls directly in the job service would couple business
state transitions and tests to one vendor. An adapter makes deterministic
mocking and failure normalization simpler. Its costs are an interface to
maintain and the possibility of pretending different providers have identical
capabilities. An interface should expose only the common contract and retain
provider-specific metadata where useful.

**Retrospective improvement:** define explicit, versioned per-job output
schemas, validate before persistence, classify malformed output separately,
and add a provider idempotency key if the vendor can honor it. Keep raw
provider response retention and prompt logging constrained by privacy policy.
No live external-provider request or credential was used in the recorded
verification.
